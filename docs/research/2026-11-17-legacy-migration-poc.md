# 기존 데이터 전환 PoC: 매핑 SQL과 검증

조사일: 2026-11-17 · 티켓: [기존 데이터 → 새 스키마 매핑과 검증](https://github.com/Gn0lee/oat/issues/527) · 결과를 쓴 곳: [기존 데이터 전환](../design/legacy-migration.md)

## 결론

매핑 규칙을 SQL로 옮겨 합성 데이터(두 가구)와 운영 데이터 복원본(세 가구)을 실제로 옮겼어요. 줄 합 트리거는 모든 가구에서 통과했어요. 운영 데이터 결과는 아래 "운영 데이터 리허설"에 따로 적었어요. 가계부 숫자는 기존 화면과 모두 같았어요: 잔액을 관리하던 지갑 7/7, 장부 × 월 수입·지출 39/39, 카테고리 합 12/12, 같은 날 순서 563/563. 보유 수량도 5/5 같았어요. 평단은 "판 뒤에 다시 산" 종목 2개에서 달랐고, 이건 기존 계산이 틀렸던 것이라 기대한 차이예요. 같은 날 매도를 먼저 입력한 종목은 새 정렬 순서로 보유 수량이 음수가 되었고, 그날 매수를 앞으로 당기는 규칙으로 해결했어요.

## 환경

- 기존 DB: Docker `public.ecr.aws/supabase/postgres:17.11.0.006`에 이 레포의 `supabase/migrations` 73개를 모두 적용했어요. 이미지에 없는 `auth.jwt()`만 직접 만들었어요.
- 새 DB: Docker `postgres:18`. 물리 DB 스키마에서 전환에 필요한 테이블만 옮긴 `new-schema.sql`이에요. 두 칸 FK, 주요 CHECK, 줄 합 지연 트리거는 넣었고 RLS·롤·감사 기록은 뺐어요.
- 연결: 새 DB에서 `postgres_fdw`로 기존 DB를 `legacy` 스키마로 읽어요(`setup-fdw.sql`). 외부 테이블이 쓰는 기존 enum 타입은 새 DB에도 같은 이름으로 만들어요(`run.sh`).
- 실행: `./run.sh <전환일>`이 새 스키마를 만든 뒤 환율 백필 자리(`fx-seed.sql`, 합성)를 채우고, 가구마다 `migrate-household.sql`을 트랜잭션 하나로 돌려요. 검증은 `verify.sql`이고 결과는 `verify-output.txt`예요.

## 합성 데이터(`legacy-synthetic.sql`)

- 가계부 기록은 기존 앱의 쓰기 함수 `write_ledger_entry`를 그대로 불러서 만들었어요. 그래야 저장 잔액이 실제 앱과 똑같이 움직여요. 매매와 잔액 맞춤은 앱(TS) 코드가 하던 일을 SQL로 흉내 냈어요.
- 가구 둘: 두 사람 가구(장부 셋: 기본 공용·개인·여행 공용) 하나와 한 사람 가구 하나예요.
- 기간·규모: 2026-01~10, 가계부 기록 563건(지출 463, 수입 40, 이체 30, 비지출 출금 30), 매매 13건, 잔액 맞춤 2건.
- 일부러 넣은 경우:
  - 잔액 모름 통장
  - 결제 방법 "선택 안 함" 지출
  - 연결 통장 없는 체크카드
  - 체크카드 비지출 출금(기존 앱은 어떤 잔액도 바꾸지 않음)
  - 같은 카드사·결제일 카드 두 장, 결제일 없는 카드
  - 카드 결제일의 비지출 출금(카드대금)
  - 처음엔 잔액이 비어 있다가 쓰면서 추적된 상품권(음수)
  - 개인 장부가 없는 가구원
  - 매매: 전량 매도 후 재매수, 부분 매도 후 매수, USD 소수점 매매, 같은 날 매도 먼저 입력, 0원 매수

## 해석

- 기존 앱의 잔액 갱신 규칙에는 예외가 많아요: 체크카드 비지출 출금, 결제수단 잔액의 0부터 추적, 매매의 통화 무시. 그래서 "기록을 다시 계산해서 기존 잔액을 맞추는" 대신 "저장 잔액을 믿고 차이를 시작 잔액 맞춤 한 건으로 메우는" 방식이 정확했어요. 대신 그 차이가 첫 다리 날짜에 몰리므로, 잔액 관리를 중간에 켠 지갑은 과거 월별 자산 추이가 실제와 달라요.
- 기존 holdings 뷰는 순서를 보지 않고 합만 내서, 입력 순서 문제는 기존 화면에서 드러나지 않았어요. 새 모델에서 처음 드러나는 문제라 전환에서 걸러야 해요.

## 운영 데이터 리허설

2026-11-18에 운영 DB의 `public` 데이터만 덤프했어요. 비밀값이 있을 수 있는 시스템 설정, 알림, 푸시 구독, 종목 마스터는 뺐어요. 덤프는 로컬 컨테이너에 복원해서 같은 스크립트를 돌렸고(`LEGACY=mig527-prod ./run.sh 2026-11-18`), 끝난 뒤 덤프·복원 컨테이너·옮긴 데이터를 모두 지웠어요. 아래에는 건수와 통과 여부만 적어요.

- 규모: 가구 3, 가구원 4, 장부 6, 카테고리 71, 계좌 28, 결제수단 23, 가계부 기록 667(지출 543, 수입 77, 이체 34, 비지출 출금 13), 매매 93(KRW 81, USD 12, 매도 6), 잔액 맞춤 10.
- 새 스키마: 지갑 51(통장 14, 증권 계좌 14, 현금 5(출처 미지정 3 포함), 신용카드 7, 상품권 8, 페이머니 3), 결제수단 10, 기록 830(전환이 만든 잔액 맞춤 60 포함), 다리 957, 줄 633. 세 가구 전환에 약 1.7초 걸렸어요.
- 데이터에 없던 경우: 소수 금액, 0원 매매, 연결 통장 없는 체크카드, 체크카드·신용카드 비지출 출금, 판 뒤 다시 산 종목, 같은 날 매도 먼저 입력은 모두 0건이에요. 결제 방법 없는 지출·수입은 20건, 개인 장부에서 남의 수단을 쓴 기록은 1건(전환에는 영향 없음)이었어요.

처음 돌렸을 때 어긋난 셋과 고친 방법이에요.

1. **같은 날 순서 39건**: 묶음 저장으로 생성 시각이 완전히 같은 기록이 24묶음(75건) 있었어요. 기존 화면은 동점을 기존 id로 정렬해요(`lib/api/ledger.ts` 673~675줄). 그래서 동점 안에서 기존 id 순서대로 1µs씩 벌렸어요. 그래도 2건이 남았는데, `uuidv7(시각 − clock_timestamp())`가 함수 안에서 시계를 다시 읽어 호출마다 몇 µs씩 어긋났기 때문이에요. 시각에서 UUIDv7을 직접 조립하는 함수(`mig.v7`)로 바꿔서 667/667이 되었어요.
2. **카드 갚을 돈 0**: 운영 데이터의 마지막 기록(11/8)이 결제일(11/12~15)보다 앞이라, "결제일까지 쓴 돈을 0으로" 규칙에서는 갚을 돈이 모두 0이었어요. 실제 카드는 지난 이용기간을 다음 결제일에 갚으므로 실제보다 한 달치 적은 값이에요. 결제일마다 직전 결제일까지의 이용분만 되돌리도록(한 주기 늦게) 고쳤어요.
3. **예수금을 관리하던 증권 계좌**: 저장 잔액이 있는 증권 계좌 7개 중 5개는 사용자가 실제 예수금으로 맞춘 기록이 있었고, 6개는 원화 매매만 있었어요. 지도의 "이관 증권 계좌는 예수금 관리 꺼짐"대로면 기존 화면의 예수금이 사라져서, 원화 전용 계좌는 예수금 관리를 켜고 시작 잔액 맞춤으로 맞추기로 했어요(Q10). USD가 섞인 1개는 저장값이 USD를 환산 없이 더한 값이라 꺼진 채로 둬요.

## 한계

- 합성 데이터는 제가 떠올린 경우만 담아요. 운영 데이터에서 새 경우(0원 매도, 소수 금액, 다른 가구원 수단을 쓴 개인 장부 기록 등)가 나오면 규칙을 더해요.
- 트리거는 행마다 기록 하나를 다시 검사해요(PoC). 물리 스키마의 "기록당 한 번" 최적화는 구현 때 넣고, 대량 전환 성능은 그때 다시 재요. 합성 데이터 두 가구 전환은 1초 안에 끝났어요.
- 새 `securities`는 기존 종목 설정에서 만들었어요. 실제로는 새 종목 마스터에서 `(시장, 코드)`로 찾아요.
- 환율은 합성값이에요(실제 백필은 시세 공급원 티켓).
