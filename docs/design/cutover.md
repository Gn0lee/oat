## 2. 전환 전에 갖출 것

모두 갖춰야 날짜를 잡아요.

1. **유료 Apple 개발자 계정**과 TestFlight 내부 테스트. 배우자를 App Store Connect 팀 사용자로 넣고 내부 테스터로 지정해요. 내부 테스트는 베타 심사가 없어요. 빌드 하나는 90일 쓸 수 있어서 그 전에 새 빌드를 올려요.
2. **도메인(oatday)**과 Cloudflare Tunnel 공개 주소. 앱의 API 주소와 비밀번호 재설정 메일 링크가 이 도메인을 써요([브랜드](brand.md)).
3. **메일 발송**(Resend 또는 SES) 도메인 인증. 비밀번호 재설정 메일이 실제로 도착하는지 확인해요.
4. **새 서버 운영 중**: `migrate`·`api`·`worker` 배포, pgBackRest 백업이 HDD·S3에 쌓이고 Healthchecks.io가 받는 상태.
5. **시세**: worker의 종목 마스터 동기화가 돌고 있고, `fx_rates`가 **2025-01-01부터** 빠짐없이 있어요([시세 데이터 공급원](market-data.md) 5절).
6. **비밀번호 비교 함수**: Better Auth 설정에 bcrypt 해시를 알아보는 `password.verify`가 들어 있어요(7절).
7. **두 계정 모두 이메일 인증됨**: 기존 `auth.users.email_confirmed_at`이 두 사람 모두 있어요. 미인증 계정은 비밀번호가 맞아도 로그인이 거절되고(PoC), 인증 메일 발송은 확인하지 않았어요. 미인증이면 기존 oat에서 먼저 인증해요.
8. **보관본 암호화 키**: 키를 미니 PC와 S3 밖(비밀번호 관리자)에 둬요. 미니 PC에 키가 있으면 HDD 사본은 사실상 평문이에요.
9. **전환 도구**(구현 때 만듦, 10절): 가구 필터가 있는 검증, 계정 이전과 V12, 되돌리기 스크립트, 커밋 뒤 서버 명령.

## 4. 리허설(D-3)

새로 뜬 덤프로 미니 PC의 **리허설 전용 DB**(운영 새 DB가 아님)에서 해요. 끝나면 덤프·컨테이너·리허설 DB를 모두 지워요. 리허설 데이터가 운영 pgBackRest 백업에 들어가지 않아요.

1. **3가구 전체**: 매핑 규칙의 경우를 넓게 확인해요(V0~V11).
2. **당일 형태(1가구 + 계정)**: 3단계 6·7을 그대로 돌려요. V12 통과.
3. **로그인**: 리허설 DB에 Better Auth 서버를 붙여 실제 Supabase 해시로 로그인해 봐요. 운영자 계정만 해요(배우자 비밀번호를 묻지 않음).
4. **되돌리기 → 재전환**: 커밋한 뒤 되돌리기 스크립트를 돌리고, 5절의 "0행 확인"이 모두 0인지 보고, 다시 전환해 같은 결과(V0~V12)가 나오는지 봐요.
5. **카드 규칙 입력 뒤 할 일**: 이용기간 규칙을 넣는 순간 새 청구서·카드대금 할 일이 생기는지 보고, 생기면 그 키도 9절 1번 뒤에 채워 두도록 서버 명령을 한 번 더 부르는지 정해요.

## 5. 되돌리기

- **돌아갈 수 없는 선**: 새 앱에 첫 기록(지출·수입·이체·매매·잔액 맞춤 중 무엇이든)을 적는 순간이에요. 그 뒤로 기존 oat에 돌아가려면 새 기록을 거꾸로 옮겨야 해서 하지 않아요.
- **커밋 전(7단계 검증 실패)**: 롤백으로 끝이에요. 지울 것이 없어요.
- **커밋 뒤, 선 앞(9단계 확인 실패)**: 되돌리기 스크립트(`rollback-household`)를 한 트랜잭션으로 돌려요.
  - 지우는 것
    - 그 가구의 가구 소유 행 전부와 알림 키
    - 그 가구원의 `user`·`account`·`session`·`verification`
    - 그 가구가 만든 `mig.map`·`mig.report` 행
    - 그 가구 때문에 등록한 종목 추적과 아직 돌지 않은 예약 작업
  - 남겨도 되는 전역 행: 전환이 만든 폐지 종목(`securities.listed = false`) 행, 그 종목의 종가. 다음 전환에서 같은 행을 찾아 써요.
  - **0행 확인**: 그 가구 id·가구원 이메일로 남은 행이 0개, `mig.map`에서 그 가구 원본 id가 0개.
- **실패한 날의 정리**: 10단계 정리 목록과 같고, 다음을 더해요.
  - 그날 올린 보관본(HDD·S3)을 지워요. 다시 하는 날 새로 떠요.
  - worker를 다시 켜요.
  - 기존 oat 쓰기를 다시 시작하고, Hermes를 기존 oat MCP에 다시 연결해요.
- 원인은 기존 oat에서 고치고 다른 날 1단계부터 다시 해요. 손으로 보정하지 않아요(지도 Notes).
- **선 뒤**: 문제가 보이면 새 앱에서 잔액 맞춤이나 수정으로 고쳐요. 보관본은 원인을 찾는 데만 써요.

## 7. 계정 이전

- 가구원마다 Better Auth `user` 1행 + `account` 1행을 만들어요. 칸 이름은 구현 때 Drizzle 스키마(Better Auth 생성) 기준이고, 아래는 Better Auth 기본 이름이에요.

| 새 | 기존 | 메모 |
|---|---|---|
| `user.id` | 새로 만듦: UUIDv7, 시각 = `auth.users.created_at` | 기존 `auth.users.id`와 다름. 짝은 `mig.map`(`src = 'user'`) |
| `user.email` | `auth.users.email` | 소문자로. 로그인 이메일의 정본은 `auth.users`예요(`profiles`의 이메일이 아님) |
| `user.name` | `profiles.name`(비면 이메일) | [매핑](legacy-migration.md) 3절 |
| `user.emailVerified` | `email_confirmed_at IS NOT NULL` | 2절 7번으로 둘 다 true여야 해요 |
| `user.createdAt` | `auth.users.created_at` | |
| `account.id` | 새로 만듦: UUIDv7 | |
| `account.providerId` | `'credential'` | `account.accountId = user.id` |
| `account.password` | `auth.users.encrypted_password` 그대로 | Go bcrypt `$2a$10$…` |
| `household_members.user_id` | 새 `user.id` | |

- **사전 점검**(7단계 앞, 원본에서): 두 사람 모두 `email_confirmed_at` 있음, 해시가 `$2a$`/`$2b$` 꼴, 이메일이 겹치지 않음(소문자 기준).
- **V12**(계정 검증): `user`·`account`가 가구원 수만큼(2), `account.password`가 원본 해시와 같음, `emailVerified`가 원본과 같음, 활동 가구원마다 `user_id`가 그 `user`를 가리킴.
- 서버 설정은 해시 모양으로 비교 방법을 골라요. 새로 정하는 비밀번호(변경·재설정)는 기본 scrypt로 저장되므로, 비밀번호를 바꾸면 bcrypt 해시는 자연히 사라져요. 비교 분기는 지우지 않고 둬요(몇 줄이고, 지우면 바꾸지 않은 사람이 로그인하지 못해요).

```ts
emailAndPassword: {
  enabled: true,
  requireEmailVerification: true,
  password: {
    hash: hashPassword, // better-auth/crypto 기본(scrypt)
    verify: ({ hash, password }) =>
      /^\$2[aby]\$\d{2}\$/.test(hash) ? bcrypt.compare(password, hash) : verifyPassword({ hash, password }),
  },
}
```

- **최소 길이**: Supabase 기본 최소는 6자, Better Auth는 8자예요. 로그인은 길이를 보지 않아서 6~7자 기존 비밀번호도 그대로 돼요. 8자 규칙은 새로 정할 때만 걸려요(PoC 확인).
- 소셜 로그인 identity는 기존에 없어서 옮길 것이 없어요.
- AI 연결(`ai_connections`)은 옮기지 않아요. 기존 oat MCP와 새 `/mcp`는 다른 서버라 다시 연결해요.
- 계정 추출 ②(해시)는 7단계에서만 쓰고, 10단계(통과한 날) 또는 실패한 날 정리에서 지워요. 다시 할 때는 Supabase가 살아 있으니 새로 떠요. 새 DB 안의 해시는 일반 계정 데이터와 같게 백업 35일 규칙을 따라요.

## 8. 보관본과 기존 oat 정리

- **보관본**: 2단계 덤프 ①의 암호화본이에요. 쓰임은 두 가지예요.
  - 전환 오류의 원인 찾기
  - 새 DB에 자리가 없는 정보(태그, 계좌·카드 끝 네 자리·메모, 종목 위험도, 테스트 가구 2개)
- **넣지 않는 것**: 비밀번호 해시(`auth` 스키마), 시스템 설정·알림·푸시 구독(비밀값이 있을 수 있음). 두 쓰임 어디에도 필요 없어요.
- **90일**인 이유: 전환 오류는 대부분 첫 청구서 확정과 첫 월말에 드러나요(카드 결제일 맞춤이 근사라서). 90일이면 청구서와 월말을 두세 번 겪어요. 일반 백업 35일은 첫 청구서 전에 끝날 수 있고, 1년은 목적에 비해 길어요(개인정보보호법의 "목적 달성 시 지체 없이 파기").
- **탈퇴자도 같은 기준**([가구원 나가기·계정 삭제](member-leave.md) 9절): 전환 뒤 누가 계정을 지워도 보관본에서 그 사람 몫만 골라 지우지 않아요. 보관본이 통째로 지워지는 D+90에 함께 사라져요.

| 시점 | 운영자가 할 일 |
|---|---|
| D-day ~ D+30 | 기존 oat를 읽기 전용으로 두고(입력하지 않음) 새 앱과 비교에 써요. 기존 GitHub Actions는 켜 둬요 |
| D+30 | ① 기존 DB의 가계부·매매·잔액 맞춤 `max(created_at/updated_at)`이 1단계에 적은 시각과 같은지 확인해요. 다르면(실수로 적은 기록) 그 기록을 새 앱에 손으로 옮겨 적어요. ② 보관본을 HDD·S3에서 내려받아 복원해 봐요. ③ 되면 기존 GitHub Actions → Vercel 프로젝트 → Supabase 프로젝트 순서로 내려요 |
| D+90 | 보관본을 HDD·S3에서 지우고 새 DB의 `mig` 스키마를 지워요(`drop schema mig cascade`). 그 뒤 pgBackRest 백업 35일이 지나면 대응표가 완전히 사라져요 |

## 9. 전환 직후 운영자가 할 일

앱 안내 화면을 두지 않으므로 운영자가 직접 해요. 전환 보고서(V10·V11)가 목록이에요.

1. **카드 이용기간 규칙**: 신용카드 지갑마다 이용기간 규칙을 넣어요(전환은 비워 둠). 첫 청구서 확정 때 결제일 맞춤의 근사가 맞춰져요. 리허설(4절 5번)에서 정한 대로 규칙을 넣은 뒤 알림 키를 한 번 더 채워요.
2. **잔액 모름 통장**: 실제 잔액으로 잔액 맞춤을 하거나, 이제 안 쓰는 통장은 보관해요(ADR 0018).
3. **출처 미지정 지갑**: "결제수단 모름"으로 보이는 것을 확인만 해요. 손대지 않아요.
4. **나만 보기**: 전환한 지갑은 나만 보기로 바꿀 수 없어요. 필요하면 새 지갑을 만들어요([숨긴 지갑](hidden-wallets.md) 6절). 바꾸려 하면 지갑 설정의 막힘 문구가 이유를 알려 줘요.

## 10. 구현 때 만들 전환 도구

지도 안에서는 사양만 정하고, 스크립트는 구현에서 만들어요. 매핑 PoC 스크립트(`docs/research/2026-11-17-legacy-migration-poc`)에서 출발해요.

| 도구 | 사양 |
|---|---|
| 가구 전환 | PoC `migrate-household.sql`을 실제 스키마로. `users` 자리 표 대신 7절의 `user`·`account`. 끝에서 커밋하지 않고 검증으로 이어요 |
| 검증 | `verify.sql`에 가구 필터(`:hh`)를 넣어요. 지금은 `legacy.*` 전체와 비교해서 한 가구만 옮기면 V1·V6·V7이 테스트 가구 몫만큼 어긋나요. V11의 "환율 없는 USD 매매"는 **0건**을 통과 조건으로 올려요(4단계 환율 확인과 짝). V12를 더해요 |
| 되돌리기 | `rollback-household`: 5절의 지우는 것·남기는 것·0행 확인 |
| 커밋 뒤 서버 명령 | 가구 id를 받아 알림 키 채우기와 종목 추적 등록·종가 백필 예약을 해요. 몇 번 불러도 같은 결과(멱등) |
| 덤프·복원 | 11절 |

## 11. 덤프 형식과 복원

- 형식: `pg_dump -Fc --no-owner --no-privileges --schema=public` + 제외 테이블 `-T`. 데이터만 뜨지 않고 스키마를 함께 떠요(`holdings` 뷰 등 기존 스키마째 복원해야 해요).
- 복원: 기존 PoC처럼 Supabase Postgres 이미지(운영과 같은 메이저 버전) 컨테이너에 `pg_restore --no-owner`. 기존 RLS·롤 참조가 걸리면 이 레포의 `supabase/migrations`를 먼저 적용한 빈 DB에 데이터만 복원해요. 리허설에서 어느 쪽이 되는지 정해 적어요.
- 확인: `pg_restore --list`는 읽히는지만 봐요. 통과 조건은 복원 뒤 `max(created_at)`이 1단계 시각과 같은 것이에요.

## 12. 받아들인 한계

- 기존 oat에서 잔액을 관리하지 않던 통장은 운영자가 맞출 때까지 다리 합만 보여요(ADR 0018).
- 신용카드 지갑의 갚아야 할 돈은 첫 청구서 확정 전까지 근사예요.
- 태그·끝 네 자리·메모와 테스트 가구는 D+90 뒤 어디에도 남지 않아요.
- 배우자 계정의 실제 해시 로그인은 당일 9단계에서 처음 확인해요(리허설은 운영자 계정만). 안 되면 되돌리기 대신 재설정 메일로 넘어가도 돼요. 데이터와 상관없는 문제라서요.
- 정식 출시 뒤 새 가구가 들어오는 일은 전환이 아니라 일반 가입이에요. 이 절차는 한 번만 써요.
