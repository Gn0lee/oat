## 1. 기존 데이터의 모양(전환에 영향을 주는 것만)

기존 데이터는 이 레포의 `supabase/migrations`를 끝까지 적용한 스키마다.

| 기존 | 성질 |
|---|---|
| `ledger_entries` | 한 건 = 금액 하나 + 출발(`from_account_id`·`from_payment_method_id`) + 도착(`to_*`). 종류는 지출·수입·이체·**비지출 출금**이다. 비지출 출금은 카테고리가 없고 통계에 들어가지 않는다. 지출·수입은 결제 방법을 "선택 안 함"으로 둘 수 있다. |
| 날짜 | 날짜만 입력하고, `YYYY-MM-DDT00:00:00Z`(한국 09:00)로 저장한다. 화면은 한국 날짜로 읽는다. 시각 입력은 없다. |
| 저장 잔액 | `accounts.balance`, `payment_methods.balance`(선불·상품권·현금)는 기록을 쓸 때마다 함수가 더하고 뺀다. 계좌 잔액이 NULL이면 "잔액 모름"이라 바뀌지 않는다. 결제수단 잔액은 NULL이어도 처음 쓰는 순간 0부터 추적된다. |
| 잔액 효과 | 지출·비지출 출금은 출발에서 빼고, 수입은 도착에 더한다. 체크카드 **지출**만 연결 통장에서 빠지고, 체크카드 비지출 출금은 어디서도 빠지지 않는다. 신용카드는 잔액 효과가 없다. |
| 카드대금 | 기능이 없다. 통장에서 비지출 출금으로 적었고 카드와 연결되지 않는다. 신용카드의 `issuer`·`payment_day`는 표시만 한다. |
| `transactions`(주식) | 매수·매도, 수량, 가격, 계좌. 통화는 `household_stock_settings`의 종목 통화다. 비용·환율은 없다. 앱이 계좌 잔액을 통화 환산 없이 ∓수량×가격만큼 바꿨다(USD도 그대로). |
| 평단 | `holdings` 뷰: 매수 총액 ÷ 매수 수량. 판 수량의 원가를 빼지 않는다. 보유 수량은 순서 없이 합만 낸다. |
| `balance_adjustments` | 사용자가 넣은 실제 잔액과 차이(`delta`), 맞춘 시각. 장부가 없다. |
| 그 밖 | 기록 태그(`ledger_tags`), 종목별 자산 유형·위험도(`household_stock_settings`), 계좌의 증권사·끝 네 자리·메모, 변경 요청, 알림, 푸시 구독, 쓰지 않는 `tags`·`holding_tags`·`target_allocations`. 정기 거래 기능은 없다. |

## 2. 공통 규칙

1. **트랜잭션 하나 = 가구 하나.** 한 가구를 옮기다 실패하면 그 가구만 통째로 롤백하고, 다음 가구로 넘어간다. 줄 합 트리거(ADR 0015)가 커밋할 때 모든 기록을 확인한다.
2. **ID.** 새 행은 모두 UUIDv7이다. 시각 부분은 원래 행의 생성 시각(`created_at`, 가구원은 `joined_at`)이다. 그래서 같은 날 기록의 순서가 기존 화면 순서(날짜 → 생성 시각 → id)와 같다.
   - 시각에서 UUIDv7을 직접 조립한다: 48비트 unix ms, ms 아래 12비트(RFC 9562 방식 3), 나머지 난수. `uuidv7(원래 시각 − clock_timestamp())`는 함수 안에서 시계를 다시 읽어서 호출마다 몇 µs씩 어긋나므로 쓰지 않는다.
   - 생성 시각이 완전히 같은 기록(기존 묶음 저장)은 기존 id 순서대로 1µs씩 벌린다. 기존 화면이 동점을 id로 정렬했기 때문이다. 전환이 새로 만드는 행(개인 장부, 출처 미지정 지갑, 카드 결제일 맞춤)은 지금 시각이다. 기존 id → 새 id 대응표는 전환 DB에 남긴다.
3. **날짜.** 기록 날짜 = `transacted_at`의 한국 날짜다. 기존 저장 방식(UTC 0시)에서는 입력한 날짜와 같다. 시각(`records.time`)은 비운다. 해외 주식도 사용자가 입력한 날짜를 그대로 쓴다. 기존 앱은 현지 날짜인지 한국 날짜인지 정하지 않았기 때문이다(ADR 0014는 앞으로의 입력 규칙이다).
4. **금액.** 가계부 금액은 원 단위 `bigint`이고 KRW다. 소수가 있으면 절댓값 기준 사사오입하고 보고한다. 매매 체결 금액(수량 × 가격)은 통화 최소 단위(KRW 원, USD 센트)에서 절댓값 기준 사사오입한다.
5. **새 모델에만 있는 정보는 비운다**(지도 Notes). 품목·정가·매입일·할부·매매 비용·혜택·정산이 해당한다. 회사 지원 같은 돌려받은 돈도 기존처럼 일반 수입이다.
6. **기존에 없던 숫자를 지어내지 않는다**(ADR 0018). 기존 화면에 있던 잔액은 정확히 맞추고, 없던 잔액은 사용자가 새 앱에서 처음 잔액 맞춤을 할 때부터 정확해진다.

## 3. 테이블별 매핑

| 기존 | 새 | 규칙 |
|---|---|---|
| `households` | `households` | 이름 그대로 |
| `profiles` + `household_members` | Better Auth `user` + `household_members` | 표시 이름 = `profiles.name`(비면 이메일). 역할 그대로. 사용자 계정을 만드는 방식은 전환 당일 절차에서 정한다. |
| `ledger_books` | `ledgers` | shared → 공용, personal → 개인(주인 = `created_by`). 보관한 장부는 `archived_at`을 그대로 옮긴다(물리 스키마에 칸을 더함). 기본 장부(`is_default`)는 증권 계좌의 장부가 된다. |
| `categories` | `categories` | 가구 행 그대로. 부모를 먼저 넣는다. 아이콘·정렬은 그대로 둔다. `is_system`은 옮기지 않는다(새 모델에서 기본 카테고리는 가구 행이라 고칠 수 있음). `is_fixed_default`는 모두 false다(Q5). 새 모델의 시스템 카테고리(미분류·투자 비용 등)는 새 가구 시드가 따로 넣는다. |
| `accounts`(은행) | `wallets` kind 통장 | 묶음: 적금·예금은 모으는 돈, 나머지는 쓸 수 있는 돈. `allow_member_use` = `is_household_usable`. `hidden_from_household` = false(기존에는 숨김이 없었다). |
| `accounts`(증권) | `wallets` kind 증권 계좌 + `wallet_brokerage_settings` | 증권 계좌 조건: `category = investment`, 또는 `account_type`이 stock·isa·pension, 또는 매매가 있는 계좌. 묶음은 투자. 장부는 기본 공용 장부다. **예수금 관리**는 예수금을 관리하던(저장 잔액이 있는) 원화 전용 계좌만 켜고, 나머지는 끈다(Q10, 5절). 과세 유형은 isa → ISA, pension → 연금, 나머지는 일반이다. |
| `payment_methods` 선불·상품권·현금 | `wallets` kind 페이머니·상품권·현금 | 묶음: 상품권은 포인트·상품권, 나머지는 쓸 수 있는 돈. 결제수단은 만들지 않는다(기록이 지갑을 직접 가리킴). |
| `payment_methods` 신용카드 | `wallets` kind 신용카드 + `payment_methods` + `wallet_card_settings` | 지갑은 **주인 × 카드사 × 결제일**로 묶는다(ADR 0005). 결제일이 없으면 카드마다 지갑 하나다. 지갑 이름은 카드가 하나면 카드 이름, 여럿이면 "카드사 N일 결제"다. 이용기간 규칙은 비워 두고 사용자가 확인한다. |
| `payment_methods` 체크카드 | `payment_methods` | 연결 통장의 지갑을 가리킨다. 연결 통장이 없으면 주인의 출처 미지정 지갑을 가리킨다(Q3). |
| `ledger_entries` 지출 | 기록(`general`) + 나간 다리 + 지출 줄 1 | 다리: 계좌 → 그 지갑. 신용카드 → 카드 지갑 + 다리·기록의 `payment_method_id`. 체크카드 → 연결 통장 + 결제수단. 선불·상품권·현금 → 그 지갑. 없음 → 작성자의 출처 미지정 지갑. 줄 카테고리 = 기존 카테고리. |
| `ledger_entries` 수입 | 기록 + 들어온 다리 + 수입 줄 1 | 도착이 없으면 작성자의 출처 미지정 지갑 |
| `ledger_entries` 이체 | 기록 + 다리 2(−/+) | 줄 없음 |
| `ledger_entries` 비지출 출금 | 기록 + 나간 다리 + 미분류 지출 줄 1, **통계 제외** | 기존처럼 수입·지출 통계에 들어가지 않는다. 카드대금으로 바꾸지 않는다(Q1). 체크카드 비지출 출금은 연결 통장 다리가 된다. 기존 앱이 그 통장 잔액을 바꾸지 않던 것은 시작 잔액 맞춤이 흡수한다(5절). |
| `balance_adjustments` | 기록(`balance_adjustment`) + 다리(`delta`) | 날짜 = `adjusted_at`의 한국 날짜, 장부 = 지갑 주인의 개인 장부(Q8), 제목·메모 그대로. `delta = 0`은 옮기지 않는다. |
| `transactions` | 기록(`trade`) | 6절 |
| `household_stock_settings` | `securities` 대응 | `(시장, 코드)`로 새 종목 마스터의 행을 찾는다. 종목명·통화도 거기서 온다. 자산 유형·위험도는 옮기지 않는다(Q7). |
| `ledger_entry_tags`, 계좌 증권사·끝 네 자리·메모, 결제수단 카드사·끝 네 자리·메모, 자산 유형·위험도 | 없음 | **기존 데이터 보관본**에만 남긴다(Q7). 7절 |
| 알림, 변경 요청, 푸시 구독, 초대, `tags`·`holding_tags`·`target_allocations`, 시스템 테이블 | 없음 | 옮기지 않는다. 운영 상태이거나 쓰지 않는 테이블이다. |

**쓴 사람**(Q6, ADR 0017 수정): 공용 장부의 나간 기록에서 계산값이 특정 가구원이고(카드 주인, 또는 가구원 사용 허용이 꺼진 지갑의 주인) 기존 작성자와 다를 때만 `spender_member_id`에 기존 작성자를 넣는다. 계산값이 "함께"(가구원 사용 허용이 켜진 지갑에서 결제수단 없이 나간 돈)이면 채우지 않는다. 기존 작성자는 입력한 사람이라 "함께"를 덮으면 몰아서 적는 사람에게 쏠리기 때문이다. 남의 카드를 고른 기록은 기존 앱에서 그 카드의 "가구원 사용 허용"이 필요했으므로, 작성자가 실제로 쓴 사람일 가능성이 높다.

**고정비**(Q5): 기존에 정기 표시가 없어서 모든 전환 기록의 `is_fixed`는 false다. 고정비 비중은 새 앱에서 적은 기록부터 의미가 생긴다.

**묶음**: 지갑 종류에서 나오는 기본값을 쓰되, 기존 계좌 유형의 적금·예금은 "모으는 돈"으로 둔다.

## 4. 장부

- 잔액 맞춤 기록(기존 맞춤, 시작 잔액, 카드 결제일 맞춤)은 **지갑 주인의 개인 장부**에 넣는다(Q8). 맞춤 금액에는 개인 장부 지출의 합이 섞여서, 공용 장부에 두면 다른 가구원이 개인 지출을 역산할 수 있기 때문이다. 지갑 잔액 자체에 개인 기록이 드러나는 문제는 "통계 화면 구성"에서 정한다.
- 보관하지 않은 개인 장부가 없는 가구원에게는 "<이름> 개인" 장부를 만든다. 개인 장부가 여럿이면 가장 오래된 것을 쓴다.

## 5. 잔액

잔액은 다리의 합이다. 지갑마다 아래 규칙 하나로 시작한다.

| 지갑 | 규칙 | 근거 |
|---|---|---|
| 잔액을 관리하던 통장·페이머니·상품권·현금 | **시작 잔액 맞춤** 1건 = 저장 잔액 − 옮긴 다리 합. 날짜는 지갑 생성일과 첫 다리 날짜 중 빠른 날이고, id 시각은 그보다 1초 앞이다. 차이가 0이면 넣지 않는다. | 지금 잔액은 기존 화면과 정확히 같다. 잔액 관리를 중간에 켠 계좌는 그 전 구간의 과거 잔액(월별 추이)이 실제와 다를 수 있다. 기존 데이터로는 알 수 없는 값이다. |
| 잔액을 관리하지 않던 통장(저장 잔액 NULL) | **맞춤 없음**(Q2). 다리 합이 그대로 잔액이고, 전환 보고서에 "실제 잔액 입력 필요"로 남긴다. | 0원이나 다른 숫자를 지어내지 않는다. 새 앱에서 첫 잔액 맞춤을 하면 그때부터 정확하다. |
| 신용카드 지갑 | **결제일 맞춤**(Q1): 결제일마다(결제일이 없거나 그달에 없으면 말일) 맞춤 1건. 금액은 **직전 결제일까지** 쓴 돈(그 전 결제일 다음 날 ~ 직전 결제일)을 되돌리는 값이다. 전환일 이전 결제일까지만 넣는다. | 기존 앱은 갚을 돈을 몰랐고, 카드대금은 카드와 연결되지 않은 비지출 출금이었다. 맞춤이 없으면 카드 지갑이 "지금까지 쓴 카드값 전부"만큼 음수가 된다. 실제 카드도 지난 이용기간을 다음 결제일에 갚으므로 한 주기 늦게 갚는다고 본다. 그래서 전환 시점의 갚을 돈은 대략 한 달치 + 이번 달 이용분이다. 이용기간 규칙을 모르는 근사라서 사용자가 첫 청구서를 확정할 때 맞춰진다. 처음 규칙(직전 결제일 다음 날 ~ 그 결제일을 되돌림)은 운영 데이터에서 갚을 돈이 모두 0으로 나와 실제보다 한 달치 적었다. |
| 증권 계좌: 예수금을 관리하던 원화 전용 계좌 | **예수금 관리 켬** + 시작 잔액 맞춤(저장 예수금 − 옮긴 KRW 다리 합) | 기존 화면이 "예수금"으로 보여주던 숫자이고, 사용자가 실제 예수금으로 맞춘 적도 있다(운영 데이터에서 관리 계좌 7개 중 5개). 기존 화면에 있던 잔액이라 정확히 맞춘다(Q10, ADR 0009를 고침). |
| 증권 계좌: 그 밖 | 맞춤 없음, 예수금 관리 꺼짐 | USD 매매가 섞인 계좌의 저장 예수금은 USD 금액을 환산 없이 원화에 더한 값이라 뜻이 없다. 잔액 모름 계좌는 원래 몰랐다. 현금 다리는 쌓이지만 화면과 순자산에서 숨는다. 예수금 관리를 켤 때 실제 예수금으로 시작한다(ADR 0009). |
| 출처 미지정 지갑(Q3) | 맞춤 없음, **보관 상태** | 가구원마다 하나, 필요한 경우에만 만든다(현금 종류, 이름 "출처 미지정(전환)"). 수입·지출 통계는 기존과 같고, 잔액은 화면과 순자산에서 빠진다. |

## 6. 매매

- 기록은 `trade`이고 장부는 계좌의 장부(기본 공용 장부)다. 날짜는 2절, 메모는 그대로다.
- 다리는 두 개다.
  - 현금 교환 다리: 종목 통화로 ∓ 체결 금액(최소 단위 사사오입).
  - 종목 교환 다리: ±수량 + `unit_price` = 기존 가격.
- 평단은 체결 단가 × 수량으로 계산한다(물리 스키마 3.2).
- 매매 비용 줄은 없다(새 정보, 지도 Notes).
- **USD 매매의 그날 기준환율**(Q4): 새 서버의 `fx_rates`를 과거까지 백필한 뒤 기록 날짜의 마지막 고시 환율을 `fx_rate`·`fx_rate_date`에 넣는다. 그래서 전환은 환율 백필 뒤에 돌린다. 환율을 못 찾은 매매는 보고한다.
- **0원 매수**(기존은 가격 ≥ 0을 허용): 현금 다리가 0원이 되어 매매로 적을 수 없다. 그래서 `balance_adjustment` 기록의 종목 다리(시작 평단 0)로 옮기고 보고한다. 0원 매도가 있으면 그 가구는 멈춘다(실제 데이터에서 확인).
- **같은 날 매도를 먼저 입력한 경우**(Q9): 정렬 키(날짜 → 시각 → id) 순서로 보유 수량이 음수가 되는 (계좌, 종목, 날짜) 묶음은 그날 매수를 매도보다 앞에 둔다. 그 매수 기록의 UUIDv7 시각만 묶음의 가장 이른 입력 시각 바로 앞(1ms 간격)으로 당기고, 바뀐 기록을 보고한다. 화면에 보이는 값은 바뀌지 않는다. 그래도 음수가 남으면(다른 날짜에 걸친 입력 오류) 그 가구의 전환을 멈춘다. 그러면 사용자가 기존 앱에서 날짜를 고치고 다시 돌린다.
- **평단은 기존 화면과 다를 수 있다.** 판 뒤에 다시 산 종목은 기존 계산(매수 총액 ÷ 매수 수량)이 판 주식의 원가를 빼지 않아서 틀린 값이었다. 새 평단(이동평균, ADR 0009)이 증권사 앱과 맞는 값이다. 보유 수량은 항상 같아야 한다.

## 7. 기존 데이터 보관본

전환 직전 `public` 스키마 데이터 전체를 덤프해 백업 저장소에 보관한다. 새 DB에 자리가 없는 정보(태그, 증권사·끝 네 자리·메모, 위험도 등)는 이 보관본에만 남는다(Q7). 보관 기간과 위치는 전환 당일 절차에서 정한다.

## 8. 검증

전환 스크립트 끝에 아래를 돌린다(`verify.sql`). 실패하면 전환하지 않는다.

| # | 항목 | 통과 기준 |
|---|---|---|
| V0 | 줄 합 트리거 | 모든 가구가 커밋됨(실패 가구 0) |
| V1 | 건수 | 기록 = 기존 기록, 매매 = 기존 거래, 잔액 맞춤 = 기존 맞춤(차이 0 제외) |
| V2 | 잔액을 관리하던 지갑 | 새 KRW 다리 합 = 기존 저장 잔액(예수금 관리를 켠 증권 계좌 포함, 모든 지갑) |
| V3 | 보유 수량 | 계좌 × 종목마다 새 종목 다리 합 = 기존 `holdings.quantity`. 새 쪽에만 남은 보유 0개 |
| V4 | 평단 | 판 뒤 다시 산 적 없는 종목은 기존 `avg_price`와 같음. 나머지는 차이 목록을 보고서에 남김 |
| V5 | 보유 수량 음수 | 정렬 키 순서로 다시 계산해서 0건 |
| V6 | 장부 × 월 수입·지출 | 기존 통계(지출·수입만)와 새 줄 합(통계 제외 빼고)이 모두 같음 |
| V7 | 카테고리 합 | 전 기간 카테고리별 합이 같음 |
| V8 | 같은 날 순서, UUIDv7 시각 | 장부 × 날짜 안의 순서가 기존 화면 순서(생성 시각 → id)와 같음(Q9로 당긴 매매 제외). 가계부 기록의 UUIDv7 시각 = `created_at`(ms) |
| V9 | 신용카드 지갑 | 잔액 = 직전 결제일 이전 결제일 이후 이용분(보고) |
| V10 | 잔액 모름·출처 미지정 지갑 | 목록 보고(사용자 안내용) |
| V11 | 보고 항목 | 만든 개인 장부, 출처 미지정 지갑, 당긴 매수, 0원 매수, 소수 금액, 환율 없는 USD 매매 |

합성 데이터와 운영 데이터 복원본 모두 V0~V11이 기준대로 나왔다(PoC 문서). 운영 데이터에서 처음 어긋난 셋(묶음 저장의 동점 순서, 카드 갚을 돈이 한 달치 적음, 예수금을 관리하던 증권 계좌)은 위 규칙으로 고쳤다.

## 9. 다른 티켓에 넘기는 것

- **전환 당일 절차**
  - 기존 oat 쓰기 중지 → 덤프 → 보관본 저장 → 환율 백필 확인 → 가구별 전환 → 검증 → 사용자 안내 순서.
  - 실패 가구를 처리하는 방식(기존 앱을 다시 열어 고치게 할지).
  - Better Auth 사용자 생성과 첫 로그인(비밀번호를 옮기지 않으므로 이메일 로그인·재설정).
  - 보관본의 보관 기간.
  - 전환 직후 안내: 잔액 모름 지갑의 실제 잔액, 카드 이용기간 규칙, 첫 청구서 확정.
  - 스크립트는 빈 새 DB에 한 번 돌리는 전제다(다시 돌리려면 그 가구 행을 지우고 돌린다).
- **시세 데이터 공급원 선택**
  - `fx_rates` USD/KRW를 가장 이른 USD 매매일부터 백필해야 한다.
  - 기존 종목 코드(`market`, `ticker`)로 새 `securities` 행을 찾을 수 있어야 한다. 상장폐지 종목도 포함한다.
  - → [시세 데이터 공급원](market-data.md) 5절에서 정했다: 환율은 ECOS로 2025-01-01부터 백필하고, 새 마스터에 없는 코드는 기존 `stock_master` 행에서 `listed = false`로 만든다(전환용 덤프에 `stock_master` 포함). 종가 백필은 전환 뒤에 돌린다.
- **물리 DB 스키마(이 티켓에서 반영)**: `ledgers.archived_at`을 더했다.
- **통계 화면 구성**: 카드 결제일 맞춤·시작 잔액 맞춤이 개인 장부에 있을 때 공용 지갑 잔액을 보여주는 방식. 출처 미지정 지갑 기록을 결제수단별 통계에서 어떻게 부를지.
