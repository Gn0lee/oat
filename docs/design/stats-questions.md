# 통계 질문 목록

- 결정일: 2026-11-17
- 티켓: [통계: 실제로 매달 확인하고 싶은 질문 목록](https://github.com/Gn0lee/oat/issues/509)
- 관련 ADR: 0006(돌려받은 돈은 원 기록의 달), 0007(카테고리 통계는 줄, 건수는 기록), 0008(예정은 계산), 0009(실현손익은 투자 화면에만), 0016(잔액은 묶음별, 순자산 합계는 추이에서만), 0017(고정비와 쓴 사람은 기록에 저장하는 귀속)
- 전제: [물리 DB 스키마](physical-db-schema.md). 이 문서는 "무엇을 묻는가"와 "지금 스키마로 답할 수 있는가"를 정한다. 화면 배치·차트 모양·홈에 무엇을 올릴지는 지도의 "통계 화면 구성"에서 정한다.

## 1. 질문 목록

사용자가 매달 실제로 확인하고 싶다고 고른 질문이다. 후보 16개 중 순자산 합계 하나만 빠졌다(ADR 0016).

| # | 질문 | 숫자 정의 |
|---|---|---|
| F1 | 이번 달 얼마 벌고, 얼마 쓰고, 얼마 남았나 | **수입**, **지출**, **남은 돈**(= 수입 − 지출), **남긴 비율**(= 남은 돈 ÷ 수입). "저축"·"저축률"이라는 말은 쓰지 않는다. 대출 지갑이 있으면 **갚은 대출 원금**을 한 줄 더 보여준다 |
| F2 | 어디에 많이 썼나, 평소보다 많이 쓴 곳은 | 카테고리별 지출. 평소는 직전 3개의 끝난 달 평균이 기본이다 |
| F3 | 이 속도면 이번 달 얼마 쓰게 되나 | 1일부터 오늘까지의 누적 지출을 지난달 같은 날까지의 누적과 비교한다 |
| F4 | 아낀 돈은 얼마인가 | 확정 혜택 − 혜택 회수 − 소멸 + 결제 할인(정가 − 줄 금액) |
| A1 | 묶음별로 지금 얼마 있나 | 지갑 **묶음**(쓸 수 있는 돈·모으는 돈·투자·포인트·상품권·갚을 돈)별 현재 잔액. 순자산 합계는 여기에 두지 않는다 |
| A2 | 자산이 매달 얼마나 자랐나 | 월말 기준 묶음별 잔액 추이. 순자산 합계는 **이 추이에서만** 선 하나로 보여준다 |
| A3 | 투자 수익은 어떤가 | 종목별 평가손익·수익률(계좌는 볼 수 있는 계좌를 종목별로 합산), 실현손익 |
| A4 | 배당을 매달 얼마 받았나 | 월별 배당. 세전(수입 줄)·원천징수(세금 줄)·세후(다리)를 모두 알 수 있다 |
| O1 | 누가 얼마 썼나 | 공용 장부의 지출을 **쓴 사람**별로 나눈다(ADR 0017) |
| O2 | 어느 카드·결제수단으로 얼마 썼나 | 기록의 앞단 결제수단(`records.payment_method_id`)별. 결제수단이 없으면(계좌이체·현금) 지갑별 |
| O3 | 고정비는 얼마고 비중은 | **고정비** 표시가 켜진 기록의 지출 ÷ 전체 지출(ADR 0017) |
| O4 | 아직 받을 돈과 이번 달 남은 예정은 | 예상 정산·혜택을 상대별로 합하고, 이번 달 남은 예정은 "N건 · 약 M원"으로 보여준다 |

함께 정한 표시 규칙:

- **통계 제외** 기록은 합계와 카테고리에서 빠진다(이미 정함). 통계 화면에서는 합계 아래에 "통계 제외 N건 · M원" 한 줄을 두고, 누르면 목록으로 간다. 기록 목록에서는 흐리게 표시하고 "통계 제외" 표시를 붙인다.
- **혜택·환불·정산을 지출에서 뺄지**는 ADR 0006에서 이미 정했다. 지출은 원 기록의 달에서 확정된 돌려받은 돈을 뺀 **실제 부담**이다. 원래 쓴 금액은 기록 상세의 "정산·환불·혜택 합계와 내 부담"에서 보여준다.

### 1.1 숫자를 만드는 공통 규칙

통계 숫자는 모두 같은 거름망을 거친다.

1. **카테고리·수입·지출은 줄에서 센다.** 건수, 가맹점, 결제수단, 쓴 사람은 기록 단위로 센다(ADR 0007).
2. **빼는 것**: `status = expected`(아직 받지 않은 혜택·정산), `excluded_from_stats`, 잔액 맞춤(줄이 없음), 교환 다리(매매·환전). 연결 대기 정산 줄(원 기록 없는 정산 줄)은 수입도 지출 감소도 아니다.
3. **줄이 속한 달**: 일반 줄은 그 기록의 날짜를 따른다. 환불·혜택·정산 줄은 가리키는 **원 기록의 날짜**를 따른다(ADR 0006). 원 기록이 없는 혜택 줄은 혜택 수입이고, 그 기록의 날짜를 따른다. 소멸 줄은 지출이 아니고 F4에서만 쓴다.
4. **볼 수 있는 장부만 더한다.** 권한 모듈이 장부 목록(공용 + 내 개인)을 정하고, 쿼리는 그 목록 안에서만 더한다. 돌려받은 돈은 늘 원 기록과 같은 장부에 있으므로(3절), 두 가구원이 보는 공용 통계는 같다.
5. **원화 환산**은 물리 DB 스키마 4.3을 따른다. 카테고리 통계는 줄 단위, 잔액은 다리 단위로 기록에 저장한 그날 기준환율을 쓴다. A1·A2의 평가액만 예외로, 평가 시점의 환율을 쓴다(A1은 최신 고시, A2는 그 달 마지막 고시).
6. **매매 비용**(거래세·수수료)은 지출 줄이고, 배당 원천징수는 세금 줄이라 지출에 들어간다. 실현손익은 수입·지출에 넣지 않는다(ADR 0009).

### 1.2 질문별 메모

- **F1 남긴 비율**: 수입이 0이면 비율을 보여주지 않는다. 지출이 수입보다 크면 음수로 보여준다. "모은 돈"(모으는 지갑으로 옮긴 돈)은 만들지 않기로 했다. 모으는 지갑이 없는 가구에서는 의미가 없고, 남은 돈과 섞여 헷갈리기 때문이다.
- **F1 갚은 대출 원금**: 대출 지갑에 들어간 + 다리의 합이다(잔액 맞춤 제외). 이자는 이미 지출 줄이다. 카드대금은 이미 이용일에 지출로 잡힌 돈을 갚는 것이라 넣지 않는다.
- **F3 페이스**: 돌려받은 돈도 원 기록의 날짜에 붙인다. 그래야 그달 마지막 날의 누적이 F1 지출과 같다.
- **F4 아낀 돈**: 다른 숫자에 더하는 값이 아니라 따로 보는 값이다. 원 기록 없는 혜택 수입은 F1 수입에도 들어가고 아낀 돈에도 들어간다. 정가가 없는 줄은 결제 할인이 0이다.
- **A1 묶음**: 지갑마다 사용자가 묶음을 고른다(ADR 0016). 기본값은 지갑 종류에서 나온다(3절). 예수금 관리를 끈 증권 계좌는 예수금을 빼고 종목 평가액만 더한다. 숨긴 지갑은 주인에게만 보인다. 공용 지갑의 잔액에 다른 가구원의 개인 장부 기록이 어떻게 드러나는지는 "통계 화면 구성"에서 정한다. 잔액 계산 자체는 장부와 관계없이 그 지갑의 모든 다리를 더한다.
- **A2 추이**: 월말 시점의 수량 × 그 달 마지막 거래일 종가 × 그 달 마지막 고시 환율이다. 묶음은 **지금의 묶음 설정**으로 과거를 다시 나눈다(묶음 이력은 두지 않는다). 과거 종가가 없으면 그 종목은 그 달 평가에서 빠지고 "시세 없음"으로 표시한다. 그래서 이관한 기존 보유 종목의 과거 종가 백필이 필요하다(4절).
- **O1 쓴 사람**: 범위는 공용 장부뿐이다. 그래서 두 가구원이 같은 숫자를 본다. 돌려받은 돈은 원 기록의 쓴 사람의 지출을 줄인다.
- **O2 결제수단**: 네이버페이로 카드와 페이머니를 나눠 낸 결제는 앞단 결제수단(네이버페이) 하나로 센다. 카드 한 장 단위의 혜택·실적은 다리의 결제수단으로 따로 모은다(물리 DB 스키마 5.2).
- **O4 받을 돈**: 예상 정산·혜택을 상대별로 묶고 "N일째"를 보여준다. 남은 예정은 ADR 0008처럼 정기 규칙·카드대금·배당에서 계산한다. 예상 청구액과는 따로 센다.

## 2. 지금 스키마로 답할 수 있는가

**답:** 모든 질문에 답할 수 있다. 다만 칸 넷과 도메인 규칙 하나를 더하고, 인덱스 하나를 더한다(3절). 요약 테이블은 처음에는 두지 않는다. A2만 첫 후보로 기록해 둔다.

PoC로 확인했다: Postgres 18, 축약 스키마, 7절 인덱스. 큰 가구 하나(하루 30건 × 10년 = 기록 109,500건·다리 119,257개·줄 약 10만 개)와 작은 가구 300개(가구당 3,000건)를 넣었다. 전체는 기록 100만·다리 110만·줄 95만 건이다. 측정은 큰 가구 기준이고, 같은 쿼리를 한 번 돌려 데운 뒤 `EXPLAIN ANALYZE`의 실행 시간을 읽었다. 실제 가구는 이보다 훨씬 작아서 넉넉하게 잡은 값이다. 자세한 내용은 [통계 쿼리 PoC](../research/2026-11-17-stats-query-poc.md)에 있다.

| # | 읽는 곳 | 필요한 인덱스 | PoC |
|---|---|---|---|
| F1 | 그달 기록(장부·날짜 인덱스) → 줄. 원 기록이 그달인 돌려받은 돈 줄(`lines (household_id, origin_record_id)`) | 있음 | 1.5ms |
| F2 | F1과 같고 4개월 | 있음 | 6.4ms |
| F3 | F1과 같고 날짜별로 묶음 | 있음 | F1과 같음(측정 생략) |
| F4 | F1의 줄 중 혜택·소멸 역할과 정가가 있는 줄 | 있음 | F1과 같음(측정 생략) |
| A1 | 그 가구의 모든 다리를 지갑·단위별로 더함 + 현재가·최신 환율 | 있음 | 34ms |
| A2 | 모든 다리 + 기록 날짜를 월별로 더해 누적 + 월말 종가·환율 | 있음 | **438ms**(10년치). 3년치 범위면 40ms. 요약 테이블을 쓰면 10ms |
| A3 | 증권 계좌의 교환 다리를 정렬 키 순서로 읽고 서버 계산 모듈이 이동평균을 다시 계산 | 있음 | 읽기 7.5ms |
| A4 | 그달 `dividend` 기록의 줄과 다리 | 있음 | F1과 같은 경로 |
| O1 | 공용 장부 그달 기록 → 나간 다리 → 결제수단·지갑 주인 | 있음 | 2.3ms |
| O2 | 그달 기록의 `payment_method_id` | 있음 | O1보다 가벼움 |
| O3 | F1에 `records.is_fixed` 조건 | 있음 | F1과 같음 |
| O4 | `status = expected`인 기록 → 줄 | **부분 인덱스 추가** | 11.5ms → 1.3ms |

### 2.1 왜 요약 테이블을 처음에 두지 않는가

요약 테이블은 "달마다 카테고리별 합계" 같은 계산 결과를 미리 저장해 두는 테이블이다. 읽기는 빨라지지만, 원본 기록이 바뀔 때마다 같은 트랜잭션에서 고쳐야 한다. 이 모델에서는 그 일이 특히 까다롭다.

- **카테고리·수입·지출 요약**: 10월에 받은 정산이 **9월**의 통신비를 줄인다(ADR 0006). 그래서 정산 하나를 저장하거나 지우면, 그 기록의 달이 아니라 원 기록의 달 요약을 고쳐야 한다. 원 기록의 날짜나 카테고리를 고치면 그 원 기록을 가리키는 모든 줄의 요약도 옮겨야 한다. PoC에서는 직접 계산해도 한 달이 2ms 안팎이라 이 복잡도를 감수할 이유가 없다.
- **잔액 추이 요약(A2)**: 사정이 다르다. 다리는 늘 자기 기록의 날짜에 잔액을 바꾸므로(ADR 0006: 잔액은 다리의 날짜대로), 원 기록의 달 문제가 없다. 그래서 요약 테이블을 넣는다면 첫 후보는 **지갑 × 단위 × 월의 변화량**(`wallet_month_deltas`)이다. 누적값이 아니라 그 달의 변화량이라서, 다리를 쓰고 지울 때 그 다리의 달 한 칸만 더하고 빼면 된다. 과거 날짜 기록을 끼워 넣어도 다른 달은 그대로다.
- **도입 기준**: A2의 p95가 200ms를 넘거나, 홈에서 추이를 띄우게 되면 넣는다(물리 DB 스키마 7.3 "측정한 뒤에 더한다"). 넣을 때는 다리 쓰기와 같은 트랜잭션에서 갱신하고, 전체 재계산 스크립트를 함께 둔다.

### 2.2 쿼리를 짤 때 지킬 것

- 돌려받은 돈은 **원 기록 쪽에서 출발해** 찾는다. 그달 원 기록 id 목록 → `lines.origin_record_id`로 가리키는 줄 → 그 줄의 기록이 확정인지 확인. 돌려받은 기록의 날짜로 찾으면 다음 달·다다음 달에 받은 돈을 놓친다.
- 공용 통계는 장부 목록을 IN으로 넘겨 `records (household_id, ledger_id, date, …)` 인덱스를 장부마다 한 번씩 탄다(PoC에서 Index Searches: 2).
- `SUM(bigint)`는 `numeric`이라 문자열로 온다(물리 DB 스키마 2.7). 집계 쿼리는 한 파서로 통일한다.

## 3. 스키마에 더하는 것

물리 DB 스키마 문서에 반영했다.

| 대상 | 추가 | 이유 |
|---|---|---|
| `wallets.stats_group` | 묶음: `spendable`(쓸 수 있는 돈)·`saving`(모으는 돈)·`investment`(투자)·`points`(포인트·상품권)·`liability`(갚을 돈). NOT NULL | A1·A2. 기본값은 종류에서 나온다: 통장·현금·페이머니 → 쓸 수 있는 돈, 포인트·상품권 → 포인트·상품권, 증권 계좌 → 투자, 신용카드·대출 → 갚을 돈. 자산 지갑은 앞의 넷 중에서 바꿀 수 있고, 부채 지갑은 늘 갚을 돈이다(CHECK) |
| `categories.is_fixed_default` | boolean, 기본 false | O3. 기록의 고정비 표시 기본값을 준다. 기본 카테고리 중 주거·통신·보험·구독류는 켠 상태로 넣는다 |
| `records.is_fixed` | boolean NOT NULL | O3. 저장할 때 정한다: 정기 규칙이 만든 기록이면 켜짐, 아니면 지출 줄 중 하나라도 고정비 기본값 카테고리면 켜짐. 사용자가 기록마다 바꿀 수 있다. 규칙을 지우거나 카테고리 기본값을 바꿔도 과거 기록은 바뀌지 않는다(ADR 0017) |
| `records.spender_member_id` | `household_members` FK, NULL 허용, RESTRICT | O1. 쓴 사람 덮어쓰기. NULL이면 계산한다(ADR 0017) |
| 도메인 규칙 | **환불·혜택 줄도 원 기록과 같은 장부**에만 들어간다(정산과 같다). 물리 DB 스키마 3.4 | 공용 장부 지출의 캐시백을 개인 장부에 적으면 두 가구원의 공용 통계가 달라진다 |
| 인덱스 | `records (household_id, ledger_id) WHERE status = 'expected'` | O4. 예상 상태 기록만 빠르게 찾는다 |

쓴 사람의 계산(덮어쓰기가 없을 때): 기록의 나간 다리(교환 아님) 중 금액이 가장 큰 다리를 본다. 그 다리에 결제수단이 있으면 결제수단의 주인이다(가족카드는 그 카드의 주인). 결제수단이 없고 지갑이 "가구원 사용 허용"이면 **함께**로 묶는다. 둘 다 아니면 지갑의 주인이다. "가구원 사용 허용"을 함께 쓰는 지갑의 표시로 다시 쓰므로 칸을 따로 더하지 않는다.

## 4. 다른 티켓에 넘기는 것

- **통계 화면 구성**: 이 질문들의 화면 배치, 홈에 올릴 숫자, 차트 모양, "아낀 돈"·"이번 달 남은 예정"의 위치, 공용 지갑 잔액에 개인 장부 기록이 드러나는 방식, F2 "평소" 기간과 이번 달 진행 중 비교 방식(달 초에는 누적이 평균보다 늘 작다).
- **시세 데이터 공급원 선택**: A2를 위해 보유한 적 있는 종목의 **과거 일별 종가**가 필요하다. 이관 데이터의 첫 매수일부터 백필할 수 있는 공급원인지, 상장폐지 종목은 어떻게 되는지 확인한다. → [시세 데이터 공급원](market-data.md) 3.5에서 정했다: KIS 일봉(원주가), 국내 실패 시 data.go.kr, 그래도 없으면 "시세 없음". 초대제 단계에서 미국 폐지 종목의 과거 종가는 받을 곳이 없다.
- **기존 데이터 → 새 스키마 매핑과 검증**: 이관한 기록의 `is_fixed`는 기존 정기 거래 표시나 카테고리 기본값으로 채운다. `spender_member_id`는 기존 `owner_id`가 계산값과 다를 때만 채운다. 지갑의 `stats_group`은 종류 기본값으로 둔다. → [기존 데이터 전환](legacy-migration.md) 3절에서 정했다: `is_fixed`는 모두 false, `spender_member_id`는 계산값이 "함께"가 아닐 때만, 적금·예금 통장은 "모으는 돈".
- **모바일 입력 UX 원칙**: 기록 상세의 "고정비"·"쓴 사람" 토글 위치. 입력 흐름에서 따로 묻지 않는다.
