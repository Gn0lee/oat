# 전환은 돌아갈 수 없는 선 앞에서만 되돌리고, 비밀번호 해시를 그대로 옮기며, 앱 안 전환 안내는 두지 않는다

기존 oat에서 실제로 쓰는 가구는 하나(가구원 2명)이고, 운영자가 그 가구원이다. 운영 DB의 나머지 가구 2개는 테스트 가구라 옮기지 않고 전환 보관본에만 남긴다. 그래서 전환은 "여러 사용자를 안전하게 넘기는 절차"가 아니라 "한 가구를 정확히 넘기는 운영자 런북"으로 정한다.

**돌아갈 수 없는 선은 새 앱의 첫 기록이다.** 쓰기 중지 → 덤프·보관본 → 환율·종목 확인 → worker 멈춤 → 가구 전환·계정 이전·검증 V0~V12를 한 트랜잭션에서 하고 통과할 때만 커밋 → 두 사람이 새 앱과 읽기 전용 기존 oat를 나란히 보는 확인 순서다. 검증이 실패하면 롤백으로 끝나고, 커밋 뒤 확인이 어긋나면 되돌리기 스크립트로 그 가구·계정·대응표·종목 추적 예약을 지우고 기존 oat로 돌아간다. 가구가 하나라 실패한 가구 처리는 그날 전환을 접는 것과 같고, 원인은 기존 oat에서 고친 뒤 다른 날 다시 한다(손으로 보정하지 않음). 새 앱에 기록이 생긴 뒤에는 되돌리지 않고 새 앱에서 고친다. 전환 3일 전쯤 새 덤프로 리허설한다. 리허설은 3가구 전체, 당일 형태(1가구 + 계정), 운영자 계정 실제 해시 로그인, 되돌리기 → 재전환을 모두 돌린다.

**계정은 Supabase의 이메일·bcrypt 해시·이메일 인증 여부를 Better Auth `user`·`account`(credential)로 그대로 옮긴다.** 서버의 `password.verify`가 해시 모양(`$2a$`/`$2b$`/`$2y$`)으로 bcrypt를 골라 비교하고, 새로 정하는 비밀번호는 기본 scrypt로 저장한다. 첫 로그인은 쓰던 이메일·비밀번호 그대로이고, 세션과 AI 연결은 옮기지 않는다. Better Auth 1.7.25 PoC에서 같은 비밀번호 로그인, 6자 기존 비밀번호 로그인(최소 8자는 새로 정할 때만), 변경·재설정 뒤 scrypt 전환, 미인증 계정 거절을 확인했다.

**앱 안 전환 안내 화면과 전환 할 일은 두지 않는다.** 목표는 데이터가 같게 옮겨지고 로그인이 똑같이 되는 것뿐이다. 잔액 모름 통장의 실제 잔액, 카드 이용기간 규칙은 운영자가 전환 직후 직접 넣는다. 전환한 지갑을 나만 보기로 바꾸려 하면 지갑 설정의 막힘 문구가 이유를 알려 준다(ADR 0031에서 전환 안내 화면에 적기로 한 문구를 대신함).

**전환 보관본은 암호화해 HDD·S3에 90일 둔다.** 비밀번호 해시와 비밀값이 있을 수 있는 테이블은 넣지 않고, 키는 미니 PC·S3 밖에 둔다. 전환 오류는 첫 청구서 확정과 첫 월말에 드러나므로 두세 번 겪을 기간이다. 탈퇴자도 같은 기준이라 보관본에서 한 사람 몫만 골라 지우지 않는다(ADR 0024). 기존 oat는 읽기 전용으로 30일 두고, 보관본 복원을 확인한 뒤 Vercel·Supabase·동기화 워크플로를 내린다. 90일째에 보관본과 기존 id → 새 id 대응표를 지운다.

배포는 TestFlight 내부 테스트라 유료 Apple 개발자 계정과 도메인(oatday)이 전환 전에 필요하다.

## Considered Options

- **비밀번호 재설정 메일로 첫 로그인**: 해시 비교 분기가 필요 없다. 하지만 첫 로그인이 메일을 오가야 해서 "똑같이 로그인"이라는 목표에 어긋나서 택하지 않았다. 재설정 경로는 잊었을 때를 위해 어차피 있다.
- **모든 비밀번호를 bcrypt로 통일**: 분기가 없다. 하지만 Better Auth 기본(scrypt)에서 벗어나 업그레이드 때 확인할 것이 늘어서 택하지 않았다.
- **첫 로그인 때 bcrypt를 scrypt로 다시 저장**: 분기를 나중에 지울 수 있다. 로그인 경로에 쓰기 훅을 더해야 하고 사용자가 둘이라 얻는 것이 작아서 넣지 않았다.
- **쓰기 중지 스위치(PostgREST 롤 읽기 전용, 권한 회수)**: 다른 이용자가 있으면 필요하다. 운영자가 유일한 사용 가구라 직접 멈추는 것으로 충분해서 만들지 않았다.
- **테스트 가구까지 옮김**: 지도 Notes의 "전부 옮겨요"에 가장 가깝다. 하지만 아무도 로그인하지 않을 계정과 가구가 새 DB에 생겨서 택하지 않았다. 리허설에서는 검증 범위를 넓히려고 모두 돌린다.
- **전환 안내 화면 + 홈 "확인할 것"의 전환 할 일**: 목업까지 만들었다. 사용자가 운영자 본인이라 필요 없다고 판단했다.
- **보관본 35일 / 1년**: 35일은 일반 백업과 같지만 첫 청구서 전에 끝날 수 있고, 1년은 목적에 비해 길다.
- **실패한 가구만 남기고 나머지 진행**: 가구가 여럿일 때의 기본안이다. 옮길 가구가 하나라 의미가 없다.

## Consequences

- 전환 전 조건(유료 Apple 계정, 도메인, 메일 발송, 새 서버 운영, 환율 백필, bcrypt 비교 분기)이 모두 갖춰져야 날짜를 잡는다.
- 정식 출시 뒤 새 가구는 일반 가입이고, 이 절차는 한 번만 쓴다.
- 태그·끝 네 자리·메모와 테스트 가구는 D+90 뒤 어디에도 남지 않는다.
- 전환 도구(가구 필터가 있는 검증, V12, 되돌리기 스크립트, 커밋 뒤 알림 키·종목 추적 서버 명령)는 구현에서 만든다. 지금 PoC 스크립트는 전체 가구를 비교해서 한 가구 전환에 그대로 쓸 수 없다.
- `password.verify`의 bcrypt 분기는 계속 둔다. 비밀번호를 바꾸지 않은 사람이 있는 한 필요하다.
