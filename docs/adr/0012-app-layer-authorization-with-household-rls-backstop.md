# 권한은 앱 레이어에서 판단하고, RLS는 가구 격리 안전망으로만 쓴다

권한 모듈 하나가 요청자의 접근 문맥(가구, 볼 수 있는 장부)을 계산하고, 모든 조회와 쓰기는 도메인 서비스에서 이것을 거친다. 개인 장부 프라이버시는 여기서만 강제한다. 추가로 요청마다 트랜잭션 안에서 `app.household_id`를 설정하고, 가구 소유 테이블에는 "현재 가구 행만 보임" RLS 정책 하나만 건다. 공개 서비스에서 가장 치명적인 사고인 다른 가구 데이터 노출을, 쿼리 버그 하나로는 일으킬 수 없게 하기 위해서다.

기존 oat는 권한을 전부 Supabase RLS·뷰·트리거로 강제했다. 새 서버는 그 방식을 버리고 판단을 앱 레이어로 옮겼다. 그런데 RLS를 아예 버리지는 않았으니, 이유를 모르는 사람에게는 반쯤 남긴 것처럼 보일 수 있다.

## Considered Options

- **전부 RLS(기존 방식)**: 정책·뷰·트리거가 복잡해지고 디버깅이 어렵다. Supabase JWT 구조도 다시 만들어야 한다.
- **앱 레이어만**: 가장 단순하다. 하지만 필터를 빠뜨린 쿼리 하나가 곧 가구 간 유출이 된다.
- **개인 장부도 RLS로**: 정책이 장부 공개 범위를 조인해야 해서, 기존 방식의 복잡도가 돌아온다.

## Consequences

- DB 롤을 셋으로 나눈다. `owner`(테이블 소유자, migrate 전용), `app`(api·MCP·가구가 정해진 worker 작업, RLS 적용), `system`(worker의 가구 횡단 작업 전용. 물리 DB 스키마에서 가구 목록 조회와 전역 기준 데이터 쓰기로 좁혔고, 가구 소유 테이블에는 접근하지 않는다). Postgres는 테이블 소유자에게 RLS를 적용하지 않으므로, api가 `owner`로 붙으면 안전망이 통째로 꺼진다.
- 정책은 `NULLIF(current_setting('app.household_id', true), '')`와 비교해서, 설정이 빠지면 0행이 보인다.
- 가구 소유 테이블은 모두 `household_id`를 가지고, 모든 요청은 트랜잭션으로 감싼다.
- 테스트는 운영과 같은 롤로 돌린다. 권한 모듈을 우회한 쿼리로 RLS만 단독 확인하는 테스트와, 집계 엔드포인트마다 가구원 A·B 시점으로 개인 장부를 확인하는 테스트가 필수다.
