# 정본 저장소는 PostgreSQL 하나이고, 휘발성 값은 프로세스 메모리에 둔다

기록·세션·시세 이력·작업 큐·중복 방지 키·감사 기록처럼 잃으면 안 되거나 쓰기와 원자적이어야 하는 것은 모두 PostgreSQL에 둔다. 잃어도 되는 장중 현재가 사본, 레이트리밋, 종목 마스터 사본은 API 프로세스 메모리에 둔다. Redis는 쓰지 않는다. 작업 큐도 Postgres 기반으로 해서, 기록 저장과 후속 작업 예약을 한 트랜잭션으로 커밋한다.

기존 oat가 Postgres를 쓴 건 Supabase 때문이었다. 이번에는 다른 DB와 용도별 저장소를 비교한 뒤에 다시 골랐다. 서비스의 성격(가구당 작은 데이터, 강한 일관성, 다리·줄 합 같은 관계형 제약, 월·카테고리 집계)에 맞기 때문이다. 셀프호스팅 운영 리서치는 Compose에 Redis를 넣었지만, 이 결정으로 뺀다.

## Considered Options

- **Redis 캐시·큐 추가**: 여러 인스턴스가 휘발성 상태를 공유할 때 빛나는데, 우리는 단일 박스에 단일 API다. 돈 숫자를 외부 캐시에 두면 무효화 버그가 곧 "잔액이 틀려 보이는" 사고가 된다. 백업 대상도 늘어난다.
- **SQLite + Litestream**: 단일 박스에는 진지한 후보다. 하지만 RLS 안전망(ADR 0012)이 없고, api와 worker 컨테이너가 파일 하나를 같이 쓰게 된다. pgBackRest 백업 계획도 다시 짜야 한다.
- **TigerBeetle**: 복식부기 전용 DB지만 계정·이체만 저장하고 수정·삭제가 없다. 기록은 자주 고쳐지고 줄·카테고리·예상/확정 상태가 붙어서, 결국 Postgres를 옆에 하나 더 두게 된다.
- **MySQL, 문서형 DB**: Postgres보다 나은 점이 없거나, 제약과 집계에 불리하다.

## Consequences

- 외부 시세 호출은 사용자 요청에서 빼고 worker가 한다. 장중 현재가는 `UNLOGGED` 테이블에 덮어써서 WAL과 백업을 키우지 않고, 종가는 영구 이력으로 남긴다.
- 집계는 조회 시 계산부터 하고, 느린 곳만 같은 트랜잭션으로 갱신하는 요약 테이블로 바꾼다. 그 밖의 캐시 레이어는 두지 않는다.
- API를 두 대 이상으로 늘릴 때 다시 검토한다. 그때 넣는 것은 휘발성 전용 Valkey다.
