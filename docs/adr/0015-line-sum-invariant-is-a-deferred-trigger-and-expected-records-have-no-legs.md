# 줄 합 불변식은 커밋 시점 DB 트리거로 지키고, 예상 상태는 다리 없는 기록 행이다

업무 규칙은 앱 레이어에서 지키지만(ADR 0012), "기록의 통화별 줄 합 = 교환이 아닌 통화 다리 합" 하나만은 지연 제약 트리거(`DEFERRABLE INITIALLY DEFERRED`)로 DB가 커밋 시점에 확인한다. 이 불변식이 깨지면 잔액과 통계가 영원히 어긋나고, 기록 하나만 보면 확인할 수 있어서 DB가 싸게 지킬 수 있기 때문이다. 기록·다리·줄은 여러 번의 INSERT로 저장되어 중간에는 합이 맞지 않으므로 즉시 검사가 아니라 커밋 시점 검사다.

예상 상태의 혜택·정산은 별도 테이블이 아니라 `records`의 `status = expected` 행이다. 줄(금액·카테고리·원 기록)은 있고 다리는 0개이며, 확정하면 같은 행에 다리가 생긴다. 트리거는 상태별로 확인한다(확정: 줄 합 = 다리 합, 예상: 다리 0개). 매매·환전의 맞바꾸는 다리는 `is_exchange`로 표시해 합 검사에서 뺀다.

돌려받은 돈(환불·혜택·정산)과 소멸은 기록의 종류가 아니라 **줄의 역할**이다. 회사 정산 한 번이 원 기록 여러 개를 줄마다 가리키고, 급여 안에 정산 줄이 섞이고, 포인트 전환 안에 소멸 몫이 섞이기 때문이다. 정산의 "연결 대기"도 상태로 저장하지 않고, 원 기록이 없는 정산 줄로 계산한다. 그래서 묶음 정산의 원 기록 하나를 지워도 그 줄만 연결 대기가 되고 나머지 줄의 지출 감소는 그대로다.

## Considered Options

- **모든 불변식을 앱 레이어에서만**: 단순하지만 MCP·worker·이관 스크립트 중 하나만 실수해도 숫자가 틀린 기록이 저장된다.
- **돌려받은 돈 한도, 보유 수량 음수 금지까지 트리거로**: 여러 기록을 시간 순서로 읽어야 해서 트리거가 복잡하고 디버깅이 어렵다. 도메인 서비스 + 지갑 행 잠금 + 통합 테스트로 지킨다.
- **혜택·정산을 별도 테이블로 두고 확정 때 기록을 만듦**: 테이블 모양은 깔끔하다. 하지만 목록·검색·장부 권한·감사·삭제 규칙이 두 갈래가 되어 택하지 않았다.
- **연결 대기·돌려받은 돈을 기록 단위 상태·종류로 둠**: 단순하지만 위의 섞인 기록을 표현하지 못하고, 원 기록 하나를 지우면 묶음 정산 전체가 연결 대기가 되어 택하지 않았다.

## Consequences

- 기록을 다루는 모든 코드(앱 API, MCP, worker, 이관)가 같은 검사를 통과해야 커밋된다.
- 예상 상태 기록은 잔액·통계 쿼리에서 다리가 없으므로 잔액에 자동으로 들어가지 않는다. 통계는 `status`로 거른다.
- 트리거는 기록당 한 번만 돌게 하고(트랜잭션 안에서 바뀐 기록 id를 모아 검사), 이관 같은 대량 쓰기에서 성능을 확인한다.
