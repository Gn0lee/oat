# 모바일 앱은 Expo(React Native)로 만들고, 빌드는 EAS 없이 맥에서 로컬로 한다

앱은 **Expo(React Native, TypeScript)** 하나의 코드베이스로 만든다. iOS를 먼저 내고, Android는 정식 출시 직전에 같은 코드로 이식한다. 빌드는 EAS 클라우드를 쓰지 않는다. CNG(`expo prebuild`)로 네이티브 프로젝트를 만들고 맥의 Xcode로 직접 빌드한다. 예전에 Expo에서 불편했던 건 클라우드 빌드뿐이었고, SDK 모듈·CNG·expo-router는 EAS 없이도 쓸 수 있다.

2026-09에 Shopify가 RN에서 SwiftUI·Compose로 돌아갔다. 코딩 에이전트 덕분에 같은 앱을 두 번 만드는 비용이 줄었다는 이유였다. 그래서 이 결정은 그 흐름과 반대로 보일 수 있다. 우리 판단은 이렇다. 에이전트가 줄여주는 건 코드를 쓰는 비용뿐이고, 두 플랫폼을 각각 검증하는 비용과 두 코드베이스의 동작이 어긋나는 비용은 1인 개발에 그대로 남는다. 서버와 같은 TS를 쓰는 이점도 크다. 또 이 앱은 고성능을 요구하지 않는다. 실기기 PoC에서 같은 입력 화면을 SwiftUI 기준점과 비교했는데, 키패드 연타·한글 메모 입력·바텀시트·키보드 전환 모두 체감 차이가 없었다([앱 스택 PoC](https://github.com/Gn0lee/oat/issues/521)).

## Considered Options

- **SwiftUI + Jetpack Compose 네이티브 두 벌**: 플랫폼 기능 접근이 가장 자유롭고, Shopify 사례가 있다. 하지만 위의 검증·동작 어긋남 비용이 있고, PoC에서 손맛 차이가 없어서 택하지 않았다.
- **Flutter**: UI 일관성은 좋다. 하지만 Dart라 서버와 타입을 공유할 수 없고, 위젯과 공유 확장은 어차피 네이티브로 써야 해서 택하지 않았다.
- **bare React Native(Expo 없이)**: 불편의 원인이 EAS였지 Expo 자체가 아니었다. Expo를 빼면 공식 모듈과 업그레이드 도구만 잃어서 택하지 않았다.
- **Expo Exact(Contract 언어)**: 2026-11 공개 당시 pre-alpha였다. Android가 미성숙했고, 기존 Expo 앱에 섞어 쓸 길도 없었다. 1.0과 Android 정식 지원이 나오면 다시 검토한다.

## Consequences

- 나중에 네이티브로 옮길 가능성은 열어 둔다. 옮기는 비용은 앱 안에 로직이 얼마나 있느냐로 정해진다. 그래서 계산·검증·권한을 서버에 두는 얇은 클라이언트와 언어 중립 API 계약을 서버 아키텍처에서 검토한다.
- OTA 업데이트는 초기에 쓰지 않는다. 기능을 바꾸려면 스토어에 다시 제출한다.
