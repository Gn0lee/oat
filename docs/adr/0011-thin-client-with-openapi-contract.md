# 앱은 얇은 클라이언트로 두고, API 계약은 서버 zod에서 생성한 OpenAPI를 단일 원천으로 한다

잔액, 예상 청구액, 정산, 혜택, 예정, 평단, 통계 집계, 최종 검증과 권한은 모두 서버가 계산한다. 앱은 화면과 입력, 표시 포맷만 맡고, 계산이 필요한 화면은 서버가 계산을 끝낸 전용 조회 엔드포인트로 받는다. API는 REST이고, 서버 라우트의 zod 스키마에서 OpenAPI 3.1 문서를 생성해 레포에 커밋한다. Expo 앱도 서버 코드를 import하지 않고, 이 문서에서 생성한 클라이언트만 쓴다.

같은 TS 모노레포에서 서버 타입을 직접 import하지 않는 게 이상해 보일 수 있다. 의도한 것이다. 나중에 SwiftUI·Compose로 옮길 가능성을 열어 두었고(ADR 0010), 옮기는 비용은 앱 안에 로직이 얼마나 있느냐와 계약이 언어 중립이냐로 정해진다. TS 앱을 처음부터 "미래의 Swift 앱과 같은 처지"에 두면 계약이 새지 않는다. OTA를 쓰지 않아 옛 앱이 오래 남으므로, 같은 `/v1` 안에서는 추가만 하고 CI가 커밋된 문서의 diff로 깨지는 변경을 막는다.

## Considered Options

- **tRPC**: TS끼리는 가장 편하지만 다른 언어 클라이언트를 만들 수 없다.
- **oRPC**: OpenAPI를 내보낼 수 있지만 RPC 모양이라 Swift·Kotlin 생성기와의 궁합이 불확실하다.
- **GraphQL**: 1인 운영에 비해 서버·캐시·권한 부품이 많다.
- **앱에서 계산(두꺼운 클라이언트, 오프라인 우선)**: 오프라인 입력이 되지만 잔액·검증 로직이 앱과 서버에 두 벌 생기고, 네이티브로 옮길 때 그대로 다시 써야 한다.

## Consequences

- 오프라인 입력은 지원하지 않는다. 앱은 보내지 못한 초안만 기기에 남기고, 모든 쓰기에 중복 방지 키를 붙여 재전송해도 기록이 두 번 생기지 않게 한다. 보내지 못한 새 기록은 폰 대기열에서 자동으로 다시 보내고, 수정·삭제는 온라인에서만 한다(ADR 0028).
- 계산 규칙이 바뀌어도 서버 배포만으로 옛 앱이 맞는 숫자를 보여준다. 강제 업데이트(최소 버전)는 보안과 데이터 오염에만 쓴다.
- 금액은 통화 최소 단위 정수, 소수 값은 문자열, 기록 날짜는 한국 기준 `YYYY-MM-DD`로 계약에 못 박는다. 언어마다 다른 부동소수점·시간대 처리 때문이다.
